Multithreading and Concurrency

Run work in parallel safely. Threads, lifecycle, synchronisation, locks, executors, concurrent collections, CompletableFuture and virtual threads.

01Concepts

  • Process: an independent running program with its own memory
  • Thread: a lightweight unit of execution inside a process; threads share the heap
  • Multithreading lets a program do several things at once (UI + download, many web requests) and use multiple CPU cores
  • Concurrency = dealing with many tasks at once; parallelism = running tasks literally at the same time

02Creating Threads

1. Implement Runnable (preferred)

Runnable task = () -> System.out.println("Running in " + Thread.currentThread().getName());
Thread t = new Thread(task, "worker-1");
t.start();            // start() creates a new thread; run() would execute in the CURRENT thread

2. Extend Thread

class MyThread extends Thread {
    @Override public void run() { System.out.println("Hello from thread"); }
}
new MyThread().start();

3. Callable and Future (returns a result)

Callable<Integer> job = () -> 6 * 7;
ExecutorService ex = Executors.newFixedThreadPool(2);
Future<Integer> f = ex.submit(job);
System.out.println(f.get());      // blocks until ready
ex.shutdown();
Warning

Calling run() directly does not create a new thread. Always call start(), and only once per Thread object.

05The Problem: Race Conditions

class Counter {
    int count = 0;
    void increment() { count++; }     // NOT atomic: read → add → write
}

Two threads can read the same value and both write back, losing an increment. Fixes: synchronisation, atomic classes or locks.

06synchronized

Only one thread at a time can hold an object's monitor lock.

class Counter {
    private int count = 0;

    public synchronized void increment() { count++; }     // locks on 'this'

    public void incrementBlock() {
        synchronized (this) { count++; }                  // smaller critical section
    }

    private static int total;
    public static synchronized void addTotal() { total++; }   // locks on the Class object
}
  • Synchronisation gives mutual exclusion and visibility of changes
  • Keep synchronised blocks short; never call unknown code inside them

Deadlock

Two threads each hold a lock the other needs.

// Thread 1: lock(A) then lock(B)     Thread 2: lock(B) then lock(A)  → both wait forever

Prevention: acquire locks in a consistent global order, use tryLock with timeouts, hold fewer locks.

07volatile and Atomic Classes

private volatile boolean running = true;      // writes are immediately visible to all threads

volatile guarantees visibility and ordering but not atomicity of compound actions.

AtomicInteger counter = new AtomicInteger();
counter.incrementAndGet();
counter.compareAndSet(5, 10);
AtomicLong, AtomicBoolean, AtomicReference<T>, LongAdder     // lock-free

08Inter-thread Communication

wait(), notify() and notifyAll() (inside synchronized) let threads coordinate.

synchronized (queue) {
    while (queue.isEmpty()) queue.wait();     // always wait in a LOOP
    item = queue.remove();
}
// producer: synchronized (queue) { queue.add(x); queue.notifyAll(); }

In modern code prefer BlockingQueue (ArrayBlockingQueue, LinkedBlockingQueue) which handles this for you.

09java.util.concurrent

Locks

ReentrantLock lock = new ReentrantLock();
lock.lock();
try { /* critical section */ }
finally { lock.unlock(); }             // ALWAYS in finally

if (lock.tryLock(1, TimeUnit.SECONDS)) { ... }
ReadWriteLock rw = new ReentrantReadWriteLock();   // many readers OR one writer

Executor framework (thread pools)

Creating a raw thread per task is expensive. A thread pool reuses threads.

ExecutorService pool = Executors.newFixedThreadPool(4);
List<Future<Integer>> futures = new ArrayList<>();
for (int i = 0; i < 10; i++) {
    int n = i;
    futures.add(pool.submit(() -> n * n));
}
for (Future<Integer> f : futures) System.out.println(f.get());
pool.shutdown();
pool.awaitTermination(1, TimeUnit.MINUTES);
FactoryBehaviour
newFixedThreadPool(n)n reusable threads
newCachedThreadPool()Grows on demand, reuses idle threads
newSingleThreadExecutor()One thread, tasks in order
newScheduledThreadPool(n)Delayed / periodic tasks
newVirtualThreadPerTaskExecutor()One virtual thread per task (Java 21)
ScheduledExecutorService ses = Executors.newScheduledThreadPool(1);
ses.scheduleAtFixedRate(() -> System.out.println("tick"), 0, 5, TimeUnit.SECONDS);

10CompletableFuture

Compose asynchronous steps without blocking.

CompletableFuture<String> cf = CompletableFuture
        .supplyAsync(() -> fetchUser(42))                 // runs in the common pool
        .thenApply(user -> user.getName())                // transform result
        .thenCombine(CompletableFuture.supplyAsync(() -> fetchOrders(42)),
                     (name, orders) -> name + " has " + orders.size() + " orders")
        .exceptionally(ex -> "failed: " + ex.getMessage());

cf.thenAccept(System.out::println);
CompletableFuture.allOf(a, b, c).join();                  // wait for all

11Virtual Threads (Java 21)

Lightweight threads managed by the JVM, not the OS. You can run millions of them, so blocking code becomes cheap.

Thread.startVirtualThread(() -> System.out.println("virtual"));

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> { Thread.sleep(Duration.ofSeconds(1)); return "done"; });
    }
}

Best for I/O-bound server workloads (many waiting requests). Don't pool them, and avoid long synchronized blocks around blocking calls.

12ThreadLocal

private static final ThreadLocal<SimpleDateFormat> FORMAT =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

Each thread gets its own copy. Remember to remove() in thread pools.

13Best Practices

  • Prefer immutable objects and executors over manual threads
  • Share as little mutable state as possible
  • Use higher-level tools (ConcurrentHashMap, BlockingQueue, atomics) before locks
  • Always release locks in finally; handle InterruptedException properly
  • Name your threads and shut down executors
Interview question

What is the difference between synchronized and ReentrantLock? What is the difference between wait() and sleep()?

ReentrantLock adds tryLock, timeouts, fairness and interruptible locking. wait() releases the monitor and must be called inside synchronized; sleep() keeps all locks and just pauses.

14Quick Recap

  • Use start(), never run(), to begin a thread
  • Race conditions need synchronisation, locks or atomics
  • Prefer ExecutorService, CompletableFuture and concurrent collections
  • volatile = visibility, not atomicity
  • Virtual threads make blocking I/O scale cheaply
