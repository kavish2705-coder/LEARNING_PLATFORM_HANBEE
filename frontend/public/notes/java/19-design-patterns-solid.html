SOLID Principles and Design Patterns

Write maintainable object-oriented code. The five SOLID principles and the most useful creational, structural and behavioural design patterns, with Java examples.

01Why Design Principles?

Code that merely works becomes expensive when requirements change. Principles guide you to code that is easy to change, test and understand. Design patterns are proven, named solutions to recurring design problems.

02SOLID Principles

S: Single Responsibility

A class should have one reason to change.

// Bad: mixes business logic, persistence and formatting
class Invoice { double total() {...}  void saveToDb() {...}  String toPdf() {...} }

// Good: one job each
class Invoice { double total() {...} }
class InvoiceRepository { void save(Invoice i) {...} }
class InvoicePrinter { String toPdf(Invoice i) {...} }

O: Open/Closed

Open for extension, closed for modification. Add behaviour by adding classes, not by editing tested code.

interface DiscountPolicy { double apply(double price); }
class FestivalDiscount implements DiscountPolicy { public double apply(double p) { return p * 0.9; } }
class NoDiscount implements DiscountPolicy { public double apply(double p) { return p; } }
// a new discount = a new class, no if/else chain to edit

L: Liskov Substitution

A subclass must be usable anywhere its parent is, without breaking behaviour. The classic violation: Square extends Rectangle where setting width also changes height. If a subclass must throw UnsupportedOperationException for an inherited method, the hierarchy is wrong.

I: Interface Segregation

Prefer small, focused interfaces over one large one. Clients should not depend on methods they don't use.

interface Worker { void work(); }
interface Eater { void eat(); }
class Robot implements Worker { public void work() {} }       // not forced to implement eat()

D: Dependency Inversion

Depend on abstractions, not concrete classes. High-level code should not know low-level details.

class OrderService {
    private final PaymentGateway gateway;                     // interface
    OrderService(PaymentGateway gateway) { this.gateway = gateway; }   // injected
}

Dependency Injection (DI) is the technique of passing dependencies in, instead of creating them with new. Spring does this for you (IoC container).

03Other Guiding Rules

  • DRY: Don't Repeat Yourself
  • KISS: Keep It Simple
  • YAGNI: You Aren't Gonna Need It
  • Law of Demeter: talk only to your immediate friends (a.getB().getC().doIt() is a smell)
  • Composition over inheritance
  • High cohesion, low coupling

05Creational Patterns

Singleton: exactly one instance

// Best: enum singleton (thread-safe, serialisation-safe)
public enum AppConfig {
    INSTANCE;
    public String get(String key) { return System.getProperty(key); }
}

// Or: lazy holder idiom
public class Registry {
    private Registry() {}
    private static class Holder { static final Registry INSTANCE = new Registry(); }
    public static Registry getInstance() { return Holder.INSTANCE; }
}
Warning

Singletons are global state and hard to test. In Spring, beans are singletons by default and injected, so you rarely write one by hand.

Factory: hide which class is created

interface Notification { void send(String msg); }
class Email implements Notification { public void send(String m) { ... } }
class Sms implements Notification { public void send(String m) { ... } }

class NotificationFactory {
    static Notification create(String type) {
        return switch (type) {
            case "EMAIL" -> new Email();
            case "SMS"   -> new Sms();
            default -> throw new IllegalArgumentException("Unknown " + type);
        };
    }
}

Builder: construct complex objects step by step

public class User {
    private final String name, email; private final int age;
    private User(Builder b) { name = b.name; email = b.email; age = b.age; }

    public static class Builder {
        private String name, email; private int age;
        public Builder name(String n)  { this.name = n;  return this; }
        public Builder email(String e) { this.email = e; return this; }
        public Builder age(int a)      { this.age = a;   return this; }
        public User build() { return new User(this); }
    }
}
User u = new User.Builder().name("Asha").email("a@x.com").age(21).build();

Great when a constructor would have many optional parameters. (Lombok's @Builder generates this.)

06Structural Patterns

Adapter: make incompatible interfaces work together

class LegacyPrinter { void printText(String s) { ... } }
interface Printer { void print(String s); }
class PrinterAdapter implements Printer {
    private final LegacyPrinter legacy;
    PrinterAdapter(LegacyPrinter l) { this.legacy = l; }
    public void print(String s) { legacy.printText(s); }
}

Decorator: add behaviour dynamically by wrapping

interface Coffee { double cost(); }
class Espresso implements Coffee { public double cost() { return 50; } }
class Milk implements Coffee {
    private final Coffee base;
    Milk(Coffee base) { this.base = base; }
    public double cost() { return base.cost() + 10; }
}
Coffee order = new Milk(new Milk(new Espresso()));   // 70

java.io streams (new BufferedReader(new FileReader(...))) are the textbook example.

Facade: one simple entry point to a complex subsystem

class OrderFacade { void placeOrder(...) { inventory.reserve(); payment.charge(); shipping.schedule(); } }

Proxy: a stand-in that controls access

Lazy loading, caching, security checks, remote calls. Spring AOP (@Transactional) and Hibernate lazy loading use proxies.

Composite

Treat single items and groups uniformly, as in file/folder trees and UI component trees.

07Behavioural Patterns

Strategy: swap algorithms at runtime

interface SortStrategy { void sort(int[] data); }
class Sorter {
    private SortStrategy strategy;
    Sorter(SortStrategy s) { this.strategy = s; }
    void sort(int[] d) { strategy.sort(d); }
}
// With lambdas, a Strategy is just a Function / Comparator
list.sort(Comparator.comparing(Student::getName));

Observer: notify dependents when something changes

interface Listener { void onEvent(String event); }
class EventBus {
    private final List<Listener> listeners = new ArrayList<>();
    void subscribe(Listener l) { listeners.add(l); }
    void publish(String e) { listeners.forEach(l -> l.onEvent(e)); }
}

Used in GUI events, Spring ApplicationEvent, messaging systems.

Template Method: fixed skeleton, customisable steps

abstract class DataExporter {
    public final void export() { open(); write(); close(); }   // the template
    protected abstract void write();
    protected void open() {}  protected void close() {}
}

Command

Wrap a request as an object, which enables undo, queues and scheduled jobs. Runnable is a command.

Iterator

Sequential access to elements without exposing the internal structure (Iterable / Iterator).

State

Behaviour changes when the object's internal state changes (an order moves NEW → PAID → SHIPPED).

09Choosing Patterns Wisely

  • Start with simple code; introduce a pattern when you feel a real pain (duplicated if/else, hard-to-test class, scattered object creation)
  • Name the pattern in code and docs so teammates recognise it
  • Over-engineering is also a bug: prefer a lambda to a one-method Strategy class
Interview question

How do you make a Singleton thread-safe? Can reflection or serialization break it?

Use an enum singleton or the initialization-on-demand holder idiom. Reflection and serialization can create extra instances of ordinary singleton classes; enums are immune to both.

10Quick Recap

  • SOLID: single responsibility, open/closed, Liskov, interface segregation, dependency inversion
  • Creational (Singleton, Factory, Builder), Structural (Adapter, Decorator, Facade, Proxy), Behavioural (Strategy, Observer, Template Method)
  • Depend on interfaces and inject dependencies
  • Use patterns to solve real problems, not to decorate code
