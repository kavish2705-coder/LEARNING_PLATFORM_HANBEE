JPA and Hibernate (ORM)

Map Java objects to database tables. Entities, relationships, EntityManager, JPQL, fetching, the N+1 problem, caching, transactions and Spring Data JPA.

01Why ORM?

JDBC means writing a lot of repetitive SQL and manual mapping from rows to objects. Object-Relational Mapping (ORM) does this for you.

JDBCJPA / Hibernate
SQLWritten by handGenerated (or JPQL)
Mappingrs.getString(...) everywhereAnnotations on classes
RelationshipsManual joinsNavigate with fields
Caching, dirty checkingYou build itBuilt in
Control / performance tuningMaximumNeeds understanding
  • JPA (Jakarta Persistence API) is the specification
  • Hibernate is the most popular implementation (also EclipseLink)
  • Spring Data JPA adds repositories on top of JPA

02Entities

An entity is a class mapped to a table.

@Entity
@Table(name = "students")
public class Student {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 100)
    private String name;

    @Column(unique = true, nullable = false)
    private String email;

    @Enumerated(EnumType.STRING)           // store "ACTIVE", not 0 (ordinal breaks on reorder)
    private Status status = Status.ACTIVE;

    private LocalDate dob;                 // mapped automatically

    @Transient
    private int tempScore;                 // not persisted

    @Version
    private Long version;                  // optimistic locking

    protected Student() { }                // JPA needs a no-arg constructor
    // getters / setters
}

Entity rules

  • Annotated @Entity, has an @Id, non-final class, no-arg constructor (at least protected)
  • Implement equals/hashCode carefully (use the business key or id)

Id generation strategies

03Relationships

AnnotationMeaningExample
@OneToOneOne-to-oneUser ↔ Profile
@OneToMany / @ManyToOneOne-to-manyCourse → Lessons
@ManyToManyMany-to-manyStudents ↔ Courses
@Entity
public class Course {
    @Id @GeneratedValue private Long id;
    private String title;

    @OneToMany(mappedBy = "course", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Lesson> lessons = new ArrayList<>();

    public void addLesson(Lesson l) { lessons.add(l); l.setCourse(this); }   // keep both sides in sync
}

@Entity
public class Lesson {
    @Id @GeneratedValue private Long id;
    private String title;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "course_id")             // the foreign key lives here: the OWNING side
    private Course course;
}

@Entity
public class Student {
    @ManyToMany
    @JoinTable(name = "enrollment",
               joinColumns = @JoinColumn(name = "student_id"),
               inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set<Course> courses = new HashSet<>();
}

Key ideas

  • Owning side has the foreign key and @JoinColumn; the inverse side uses mappedBy
  • Cascade (PERSIST, MERGE, REMOVE, ALL) propagates operations to children
  • orphanRemoval = true deletes children removed from the collection
  • Prefer unidirectional or carefully synchronised bidirectional mappings
  • Use a Set for @ManyToMany

04Fetch Types

LAZYEAGER
LoadedWhen first accessedImmediately with the owner
Defaults@OneToMany, @ManyToMany@ManyToOne, @OneToOne
RiskLazyInitializationException outside a sessionLoading far too much data
Tip

Make everything LAZY (@ManyToOne(fetch = LAZY)) and fetch what you need per query.

The N+1 query problem

List<Course> courses = em.createQuery("select c from Course c", Course.class).getResultList();  // 1 query
for (Course c : courses) System.out.println(c.getLessons().size());   // +N queries, one per course!

Fix with a fetch join, an entity graph, or batch fetching:

em.createQuery("select distinct c from Course c join fetch c.lessons", Course.class).getResultList();

05EntityManager and the Persistence Context

The persistence context is a first-level cache of managed entities within a transaction.

Entity states

 new ──persist()──► MANAGED ──detach()/close()──► DETACHED ──merge()──► MANAGED
                      │ remove()
                      ▼
                   REMOVED ──commit──► deleted row
@PersistenceContext EntityManager em;

Student s = new Student("Asha", "asha@mail.com");
em.persist(s);                                  // INSERT on flush/commit
Student found = em.find(Student.class, 1L);     // SELECT (or from cache)
found.setName("Aisha");                         // dirty checking: UPDATE happens automatically at commit
em.remove(found);
Student merged = em.merge(detachedStudent);
Student ref = em.getReference(Student.class, 1L);   // lazy proxy
em.flush();  em.clear();  em.refresh(found);
Note

Because of dirty checking, changing a managed entity inside a transaction updates the database without calling save.

06Transactions

EntityTransaction tx = em.getTransaction();
try {
    tx.begin();
    em.persist(a); em.persist(b);
    tx.commit();
} catch (RuntimeException e) {
    if (tx.isActive()) tx.rollback();
    throw e;
}

In JEE/Spring use declarative transactions: @Transactional on service methods. Roll-back happens on unchecked exceptions by default.

07JPQL and Criteria

JPQL queries entities and fields, not tables.

List<Student> list = em.createQuery(
        "select s from Student s where s.status = :status and s.name like :q order by s.name", Student.class)
    .setParameter("status", Status.ACTIVE)
    .setParameter("q", "A%")
    .setFirstResult(0).setMaxResults(20)          // pagination
    .getResultList();

Long count = em.createQuery("select count(s) from Student s", Long.class).getSingleResult();

// DTO projection (only needed columns)
List<StudentSummary> dtos = em.createQuery(
    "select new com.hanbee.StudentSummary(s.id, s.name) from Student s", StudentSummary.class).getResultList();

// native SQL when necessary
em.createNativeQuery("select * from students where age > ?1", Student.class).setParameter(1, 18);

// named query
@NamedQuery(name = "Student.byEmail", query = "select s from Student s where s.email = :email")

Criteria API builds queries in type-safe Java code, useful for dynamic filters.

08persistence.xml (plain JPA)

<persistence xmlns="https://jakarta.ee/xml/ns/persistence" version="3.0">
  <persistence-unit name="lmsPU">
    <class>com.hanbee.model.Student</class>
    <properties>
      <property name="jakarta.persistence.jdbc.url" value="jdbc:postgresql://localhost:5432/lms"/>
      <property name="jakarta.persistence.jdbc.user" value="user"/>
      <property name="jakarta.persistence.jdbc.password" value="password"/>
      <property name="hibernate.hbm2ddl.auto" value="validate"/>
      <property name="hibernate.show_sql" value="true"/>
    </properties>
  </persistence-unit>
</persistence>

hbm2ddl.auto: validate (safe), update, create, create-drop. Use Flyway/Liquibase migrations for production schema changes.

11Spring Data JPA

Define an interface; Spring implements it.

public interface StudentRepository extends JpaRepository<Student, Long> {
    Optional<Student> findByEmail(String email);
    List<Student> findByStatusOrderByNameAsc(Status status);
    Page<Student> findByNameContainingIgnoreCase(String q, Pageable pageable);
    boolean existsByEmail(String email);

    @Query("select s from Student s join fetch s.courses where s.id = :id")
    Optional<Student> findWithCourses(@Param("id") Long id);
}
@Service
public class StudentService {
    private final StudentRepository repo;
    public StudentService(StudentRepository repo) { this.repo = repo; }

    @Transactional
    public Student register(String name, String email) {
        if (repo.existsByEmail(email)) throw new IllegalStateException("Email in use");
        return repo.save(new Student(name, email));
    }

    @Transactional(readOnly = true)
    public Page<Student> search(String q, int page) {
        return repo.findByNameContainingIgnoreCase(q, PageRequest.of(page, 20, Sort.by("name")));
    }
}

12Common Pitfalls

  • LazyInitializationException: accessing a lazy field after the session closed. Fetch what you need inside the transaction
  • N+1 queries: use fetch joins / entity graphs, check with show_sql
  • Using EAGER everywhere
  • Exposing entities directly in REST APIs. Use DTOs
  • Forgetting equals/hashCode or breaking them with generated ids
  • CascadeType.REMOVE on @ManyToMany deleting shared data
  • Large batch inserts without batching (hibernate.jdbc.batch_size) and flush/clear

13Quick Recap

  • JPA is the spec; Hibernate implements it; Spring Data JPA removes repository boilerplate
  • Entities map to tables with @Entity, @Id, @Column, relationship annotations
  • The owning side holds the foreign key; the other side uses mappedBy
  • Prefer LAZY fetching and fix N+1 with join fetch
  • Managed entities are dirty-checked automatically inside @Transactional methods
