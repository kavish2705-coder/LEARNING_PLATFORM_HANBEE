JVM Internals, Reflection and Annotations

What happens inside the JVM. Memory areas, class loading, garbage collection and tuning, then reflection, annotations and common memory problems.

02Class Loading

Classes are loaded lazily, the first time they are needed.

PhaseWhat happens
LoadingClass loader reads the .class file
LinkingVerify bytecode → Prepare static fields (defaults) → Resolve references
InitialisationStatic variables get values, static blocks run

Built-in class loaders

LoaderLoads
BootstrapCore JDK classes (java.base)
Platform (was Extension)Other JDK modules
Application (System)Your classpath / modulepath

The parent delegation model: a loader first asks its parent; only if the parent cannot find the class does it try itself. This stops anyone replacing java.lang.String.

03Runtime Memory Areas

AreaShared?Holds
HeapAll threadsAll objects and arrays. Garbage collected.
MetaspaceAll threadsClass metadata (native memory since Java 8, replaced PermGen)
Thread stackPer threadStack frames: local variables, parameters, return addresses
PC registerPer threadAddress of the current instruction
Native stackPer threadFrames for native methods
void demo() {
    int x = 10;                       // x lives in the stack frame
    Student s = new Student("Asha");  // reference s on the stack; the object on the heap
}

Heap generations

Young Generation                       Old (Tenured) Generation
┌────────┬──────────┬──────────┐      ┌─────────────────────┐
│  Eden  │ Survivor0│ Survivor1│ ───► │  long-lived objects │
└────────┴──────────┴──────────┘      └─────────────────────┘
 new objects        survive minor GCs      survive many GCs
  • New objects start in Eden
  • A minor GC copies survivors between survivor spaces and ages them
  • Objects reaching an age threshold are promoted to the old generation
  • A major/full GC cleans the old generation (more expensive)

04Garbage Collection

The GC finds objects no longer reachable from GC roots (stack variables, static fields, active threads) and reclaims their memory.

Reachability

Strong reference (normal) → Soft (cache, cleared when memory is low) → Weak (WeakHashMap, cleared at next GC) → Phantom (cleanup hooks).

WeakReference<byte[]> ref = new WeakReference<>(new byte[1024]);

Collectors

GCCharacteristicsGood for
SerialSingle threadTiny apps
ParallelMulti-thread, throughput focusBatch jobs
G1 (default since Java 9)Region-based, predictable pausesGeneral servers
ZGCPauses typically under a millisecond, huge heapsLow latency
ShenandoahConcurrent compaction, low pausesLow latency

Common JVM options

java -Xms512m -Xmx2g -XX:+UseG1GC -jar app.jar
-Xms  initial heap          -Xmx  maximum heap          -Xss  thread stack size
-XX:+UseZGC                  -XX:MaxMetaspaceSize=256m
-XX:+HeapDumpOnOutOfMemoryError
-Xlog:gc*                     # GC logging

05JIT Compilation

The JVM starts by interpreting bytecode and profiles which methods are hot. The JIT compiler (C1 and C2) compiles them to optimised machine code, using techniques like inlining and escape analysis. This is why Java programs get faster after a warm-up period.

06Memory Problems

ProblemCauseFix
OutOfMemoryError: Java heap spaceToo many live objects / leakHeap dump, fix leak, raise -Xmx
OutOfMemoryError: MetaspaceToo many classes (leaky class loaders)Fix redeploy leaks
StackOverflowErrorInfinite or very deep recursionAdd base case, use iteration
Memory leakObjects kept reachable by mistakeStatic collections, unclosed resources, listeners, ThreadLocals

Typical leak sources

  • Static Map or List that only grows
  • Listeners or callbacks never deregistered
  • Unclosed streams, connections and statements
  • ThreadLocal values left in pooled threads

Diagnostic tools

jps, jstack (thread dumps), jmap (heap dump), jcmd, jstat, VisualVM, JConsole, JDK Flight Recorder, Eclipse MAT.

07Reflection

Reflection lets code inspect and manipulate classes, methods and fields at runtime. Frameworks (Spring, Hibernate, JUnit, Jackson) depend on it.

Class<?> c = Class.forName("com.hanbee.lms.Student");   // also: Student.class, obj.getClass()

c.getName();  c.getSimpleName();  c.getSuperclass();  c.getInterfaces();
Field[] fields = c.getDeclaredFields();
Method[] methods = c.getDeclaredMethods();
Constructor<?>[] ctors = c.getDeclaredConstructors();

Object obj = c.getDeclaredConstructor(String.class).newInstance("Asha");

Method m = c.getMethod("introduce");
m.invoke(obj);

Field f = c.getDeclaredField("name");
f.setAccessible(true);                // bypasses private (restricted by modules)
f.set(obj, "Ravi");

Uses and costs

UsesCosts
Dependency injection, ORM mapping, serialisation, testing frameworks, pluginsSlower than direct calls, no compile-time checks, breaks encapsulation, strongly limited by modules

08Annotations

Annotations attach metadata to code. They do nothing by themselves; a tool, compiler or framework reads them.

Built-in annotations

AnnotationPurpose
@OverrideCompile-time check of overriding
@DeprecatedMarks API as obsolete
@SuppressWarnings("unchecked")Silence a warning
@FunctionalInterfaceEnforce one abstract method
@SafeVarargsSuppress heap-pollution warnings

Custom annotation

@Retention(RetentionPolicy.RUNTIME)     // visible at runtime
@Target(ElementType.METHOD)             // allowed on methods
public @interface Audit {
    String action() default "";
    int level() default 1;
}

class Service {
    @Audit(action = "delete-user", level = 3)
    void deleteUser(long id) { }
}

Reading annotations with reflection

for (Method m : Service.class.getDeclaredMethods()) {
    Audit a = m.getAnnotation(Audit.class);
    if (a != null) System.out.println(m.getName() + " → " + a.action());
}
Meta-annotationControls
@RetentionSOURCE, CLASS, or RUNTIME
@TargetWhere it can be placed
@InheritedSubclasses inherit it
@Documented, @RepeatableJavadoc inclusion / multiple uses

09Proxies and Class Loading Tricks

  • Dynamic proxy (java.lang.reflect.Proxy): create an implementation of an interface at runtime. Spring AOP uses proxies for @Transactional.
  • ServiceLoader: discover implementations of an interface through META-INF/services (plug-in pattern).

10Cloning and Weak/Soft Caches (brief)

  • Cloneable + clone() is error-prone; prefer copy constructors or factory methods
  • WeakHashMap and SoftReference suit memory-sensitive caches

11Quick Recap

  • Objects live on the heap, method frames on thread stacks, class data in Metaspace
  • GC reclaims unreachable objects; G1 is default, ZGC for low latency
  • Parent delegation protects core classes
  • Reflection inspects code at runtime; annotations add metadata that frameworks read
  • Most memory leaks are objects held reachable by long-lived references
