Server Components, SSR and React Frameworks

Rendering strategies from CSR to SSR and streaming, React Server Components, Server Actions, hydration, and how Next.js and React Router framework mode put it all together.

01Rendering Strategies

StrategyWhere HTML is builtWhenGood for
CSR (Client-Side Rendering)BrowserAt runtimeDashboards behind login, highly interactive apps
SSR (Server-Side Rendering)ServerEvery requestPersonalised, SEO-critical pages
SSG (Static Site Generation)Build machineAt build timeBlogs, docs, marketing pages
ISR / revalidationServerStatic, refreshed periodicallyCatalogs, news

RSC (Server Components)Server, as a component payloadPer request or buildLess client JavaScript, direct data access

Client-side rendering problems

A pure SPA ships an empty <div id="root"> and a large JavaScript bundle. The user sees a blank page until JS downloads, runs and fetches data, which hurts first paint, SEO and slow devices. Server rendering fixes this.

02SSR and Hydration

  1. Server renders the component tree to HTML and sends it, so the user sees content immediately
  2. Browser downloads the JavaScript bundle
  3. React hydrates: attaches event handlers to the existing HTML and makes it interactive
// Client entry for an SSR app
import { hydrateRoot } from "react-dom/client";
hydrateRoot(document.getElementById("root"), <App />);

// Server (simplified)
import { renderToPipeableStream } from "react-dom/server";
const { pipe } = renderToPipeableStream(<App />, { onShellReady: () => pipe(res) });

Hydration mismatches

The HTML from the server must match what React renders on the client. Mismatches come from:

  • Date.now(), Math.random(), typeof window checks during render
  • Browser-only data (localStorage) read during render
  • Invalid HTML nesting (<div> inside <p>)

Fix by moving browser-only logic into useEffect, using useId for ids, or suppressHydrationWarning for unavoidable text like timestamps. React 19 prints a readable diff for these errors.

03Streaming and Suspense

The server can send the page shell first and stream slower parts as their data becomes ready.

export default function Page() {
  return (
    <>
      <Header />                                   {/* sent immediately */}
      <Suspense fallback={<CourseSkeleton />}>
        <Courses />                                {/* streamed in when its data resolves */}
      </Suspense>
    </>
  );
}

Each <Suspense> boundary is an independent loading unit, and selective hydration lets React hydrate the parts the user interacts with first.

04React Server Components (RSC)

Server Components render only on the server (or at build time). They send a compact description of their output to the client; their code never ships to the browser.

Server vs Client Components

Server Component (default in RSC frameworks)Client Component ("use client")
Runs onServer onlyServer (for the first HTML) and browser
Can useasync/await, DB, file system, secretsuseState, useEffect, event handlers, browser APIs
Ships JS to browserNoYes
InteractiveNoYes
HooksNo state/effect hooksAll hooks
// app/courses/page.jsx: Server Component (async, talks to the database directly)
import { db } from "@/lib/db";
import EnrollButton from "./EnrollButton";

export default async function CoursesPage() {
  const courses = await db.course.findMany();          // secrets and DB access stay on the server
  return (
    <ul>
      {courses.map(c => (
        <li key={c.id}>
          {c.title}
          <EnrollButton courseId={c.id} />              {/* Client Component island */}
        </li>
      ))}
    </ul>
  );
}
// EnrollButton.jsx: Client Component
"use client";
import { useState } from "react";

export default function EnrollButton({ courseId }) {
  const [done, setDone] = useState(false);
  return <button onClick={() => setDone(true)}>{done ? "Enrolled" : "Enroll"}</button>;
}

The "use client" boundary

  • Put "use client" at the top of a file to mark it, and everything it imports, as client code
  • Push it as low in the tree as possible: keep pages/layouts as Server Components and make only interactive leaves clients
  • Server Components can render Client Components and pass serialisable props (strings, numbers, plain objects, Promises, JSX), not functions or class instances
  • A Client Component cannot import a Server Component, but it can receive one as children
"use client";
export default function Modal({ children }) {         // children can be Server Components
  const [open, setOpen] = useState(false);
  return open ? <div className="modal">{children}</div> : null;
}

Benefits

  • Smaller bundles: heavy libraries (markdown, date, syntax highlighting) stay on the server
  • Direct, secure data access with no extra API layer for reads
  • No waterfalls: fetch in parallel on the server next to the data
  • Great default for SEO and performance

Passing promises to Client Components

// Server Component
export default function Page() {
  const commentsPromise = getComments();                // not awaited
  return <Suspense fallback="…"><Comments commentsPromise={commentsPromise} /></Suspense>;
}
// Client Component
"use client";
export function Comments({ commentsPromise }) {
  const comments = use(commentsPromise);                // suspends until resolved
  return comments.map(c => <p key={c.id}>{c.text}</p>);
}

cache and request deduping

cache(fn) memoises a function per request so several Server Components can call getUser() without repeating the query. (cacheSignal, added in 19.2, tells you when a cache entry is no longer needed.)

05Server Functions (Server Actions)

A function marked "use server" runs on the server but can be called from the client like a normal async function; the framework creates the network request for you.

// actions.js
"use server";
import { revalidatePath } from "next/cache";      // framework-specific helper

export async function enroll(courseId, formData) {
  const session = await getSession();             // always authenticate here
  if (!session) throw new Error("Unauthorised");
  await db.enrollment.create({ data: { courseId, userId: session.userId } });
  revalidatePath("/courses");
}
// Used directly as a form action: works even before JavaScript loads (progressive enhancement)
import { enroll } from "./actions";
<form action={enroll.bind(null, course.id)}><button>Enroll</button></form>

Combine with useActionState, useFormStatus and useOptimistic for pending UI and optimistic updates.

Warning

Server Functions are public HTTP endpoints. Treat their arguments as untrusted input: authenticate, authorise and validate (Zod) every call. Don't rely on "only my UI calls this".

DirectiveMeaning
"use client"This module and its imports run on the client
"use server"Exported async functions are Server Functions callable from the client
(none)Server Component in RSC frameworks
Note

There is no "use server" directive for marking Server Components. It only marks Server Functions.

07React Router Framework Mode

React Router v7's framework mode adds SSR, file-based routes, loaders/actions on the server and type-safe routes on top of Vite.

// app/routes/course.tsx
import type { Route } from "./+types/course";

export async function loader({ params }: Route.LoaderArgs) {
  return { course: await db.course.find(params.id) };            // runs on the server
}
export async function action({ request }: Route.ActionArgs) {
  const form = await request.formData();
  await enroll(form.get("courseId"));
}
export default function Course({ loaderData }: Route.ComponentProps) {
  return <h1>{loaderData.course.title}</h1>;
}

08Choosing a Setup

ProjectPick
Logged-in dashboard / internal toolVite + React Router + TanStack Query (CSR)
Public site that needs SEO and speedNext.js or React Router framework mode
Content/marketing site, few interactive partsAstro (React islands) or static Next.js
Mobile appExpo (React Native)
Existing backend (Java/Spring, Django…) serving APIsSPA with Vite, or Next.js as a BFF (backend-for-frontend)
Tip

For an LMS with a separate API (such as Spring Boot or Supabase), a Vite SPA or Next.js frontend both work. Choose Next.js when public SEO pages (course catalogue, landing pages) matter.

10SEO Basics

  • Server-render or pre-render public pages
  • Unique <title> and <meta name="description"> per page (React 19 metadata tags, or the framework's metadata API)
  • Open Graph tags for sharing, canonical URLs, sitemap.xml, robots.txt
  • Semantic HTML (<main>, <h1>…), fast Core Web Vitals

11Core Web Vitals

Improve with server rendering, image optimisation, code splitting, width/height on media, and transitions for heavy updates.

12Quick Recap

  • CSR ships an empty shell; SSR/SSG send HTML first and hydrate afterwards; streaming sends the shell then the slow parts
  • Server Components run only on the server (no client JS, direct data access); mark interactive code with "use client" and keep that boundary low
  • "use server" functions are callable from the client but are public endpoints: authenticate and validate
  • Next.js (App Router) and React Router framework mode provide routing, data loading and SSR out of the box
  • Pick the simplest setup that satisfies your SEO and performance needs
