Performance and Optimisation

Understand why components re-render, then optimise with the React Compiler, memo, useMemo, useCallback, transitions, lazy loading, Suspense and list virtualisation.

01How Rendering Performance Works

Rendering means React calls your component functions. React is fast by default, and most apps need little optimisation. Optimise only after measuring a real problem.

When does a component re-render?

  1. Its state changes
  2. Its parent re-renders (even if its props are identical)
  3. A context it consumes changes
  4. A hook it uses (like useSyncExternalStore) reports a change
Parent re-renders ──► every child re-renders by default (unless memoised)

Render vs commit

Re-rendering is a calculation (cheap). Only differences are committed to the DOM. A re-render is a problem only when the calculation is slow or the tree is huge.

02Measure First

  • React DevTools Profiler: record interactions, see which components rendered and why ("Highlight updates when components render" also helps)
  • Browser Performance tab and Lighthouse
  • React Performance Tracks (React 19.2) in Chrome DevTools show scheduler and component timings
  • Test with production builds (npm run build && npm run preview): development mode is slower

03React Compiler

The React Compiler (stable v1.0) is a build-time tool that automatically memoises components and values so you rarely write useMemo, useCallback or memo by hand.

npm install -D babel-plugin-react-compiler
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react({ babel: { plugins: [["babel-plugin-react-compiler"]] } })],
});
  • It works when your components follow the Rules of React (pure rendering, no mutation of props/state)
  • Check compatibility with npx react-compiler-healthcheck@latest
  • Use the eslint-plugin-react-hooks compiler rules to find code it cannot optimise
  • You can still use manual memoisation as an escape hatch; the compiler respects it
Note

With the compiler enabled, treat useMemo/useCallback/memo as fine-tuning tools, not defaults. The sections below matter when you do not use the compiler or need precise control.

04React.memo

Skips re-rendering a component when its props are shallowly equal to last time.

import { memo } from "react";

const CourseCard = memo(function CourseCard({ course, onSelect }) {
  console.log("render", course.id);
  return <button onClick={() => onSelect(course.id)}>{course.title}</button>;
});

memo is useless if you pass new object/array/function identities every render:

<CourseCard course={{ id: 1 }} onSelect={() => go()} />    // new props each time: memo never helps

Combine with useCallback/useMemo to keep props stable.

05useMemo

Caches the result of a calculation between renders until dependencies change.

const visible = useMemo(
  () => courses.filter(c => c.title.toLowerCase().includes(query.toLowerCase())),
  [courses, query]
);

Use for:

  • Genuinely expensive calculations (measure first, e.g. filtering thousands of items)
  • Keeping an object/array identity stable for memo children or effect dependencies

06useCallback

Caches a function between renders.

const handleSelect = useCallback((id) => {
  setSelectedId(id);
}, []);                                      // stable identity across renders

<CourseCard course={c} onSelect={handleSelect} />   // memo works now

useCallback(fn, deps) is the same as useMemo(() => fn, deps).

Memoisation cheat sheet

ToolCachesSkips
memo(Component)Component outputRe-render when props are equal
useMemo(fn, deps)A computed valueRe-computation
useCallback(fn, deps)A function referenceCreating a new function identity
Warning

Memoisation has a cost (memory + comparisons). Don't wrap everything. Use it where profiling shows a benefit, or let the compiler do it.

07Cheaper Fixes Before Memoising

  1. Move state down: keep state in the smallest component that needs it, so fewer components re-render
  2. Lift content up with children: a component that receives children as a prop does not re-render its children when its own state changes
function Slider({ children }) {                // moving state lives here
  const [x, setX] = useState(0);
  return <div onPointerMove={e => setX(e.clientX)}>{children}</div>;   // children don't re-render
}
<Slider><ExpensiveTree /></Slider>
  1. Avoid creating huge inline objects/arrays that are passed to memoised children
  2. Split large components; keep render functions light
  3. Avoid unnecessary effects that set state (extra renders)

08Transitions: Keep the UI Responsive

useTransition marks a state update as non-urgent, so urgent updates (typing, clicking) stay responsive while heavy updates render in the background.

function SearchPage() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState([]);
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    setQuery(e.target.value);                              // urgent: input stays smooth
    startTransition(() => {
      setResults(filterHugeList(e.target.value));          // non-urgent: can be interrupted
    });
  }

  return (
    <>
      <input value={query} onChange={handleChange} />
      {isPending && <Spinner />}
      <ResultList items={results} />
    </>
  );
}

In React 19, startTransition can wrap async functions (Actions), with isPending covering the whole async operation.

useDeferredValue

Defers re-rendering with a value: the UI first shows the old value, then updates in the background.

const deferredQuery = useDeferredValue(query);
const results = useMemo(() => filter(list, deferredQuery), [deferredQuery]);
const stale = query !== deferredQuery;

React 19 adds an initial value: useDeferredValue(value, initialValue).

09Code Splitting: lazy and Suspense

Don't ship every page's code on the first load. Load components on demand.

import { lazy, Suspense } from "react";

const Dashboard = lazy(() => import("./pages/Dashboard"));
const Reports = lazy(() => import("./pages/Reports"));

function App() {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      <Routes>
        <Route path="/dashboard" element={<Dashboard />} />
        <Route path="/reports" element={<Reports />} />
      </Routes>
    </Suspense>
  );
}
  • Split by route first, then heavy widgets (charts, editors, maps)
  • The module must export default the component
  • Wrap in <Suspense> to show a fallback; add an Error Boundary for failed chunk loads
  • Preload on hover/intent for a snappier feel: import("./pages/Reports")

10Suspense for Data

<Suspense> also handles data (with use(), framework loaders and libraries like TanStack Query).

<Suspense fallback={<Skeleton />}>
  <Comments postId={id} />        {/* may suspend while loading */}
</Suspense>

Nest several boundaries so parts of the page appear as soon as they are ready instead of waiting for everything.

11Activity (React 19.2)

<Activity> hides parts of the UI while keeping their state and lowering their priority.

import { Activity } from "react";

<Activity mode={tab === "inbox" ? "visible" : "hidden"}>
  <Inbox />
</Activity>

Hidden content unmounts its effects and defers updates but keeps state and DOM, which is great for tabs and pre-rendering the next page.

12Large Lists: Virtualisation

Rendering thousands of rows is slow no matter how well you memoise. Virtualise: render only the visible rows.

  • TanStack Virtual, react-window, react-virtuoso
  • Or paginate / infinite-scroll with a server
import { useVirtualizer } from "@tanstack/react-virtual";

const rowVirtualizer = useVirtualizer({
  count: rows.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 48,
});

15Common Performance Mistakes

MistakeBetter
Memoising everything "just in case"Measure; use the compiler
New object/function props to a memo childStabilise with hooks or restructure
Putting high-frequency state high in the treeMove state down
Huge lists without virtualisationVirtualise or paginate
Effects that set derived stateCompute during render
Big libraries imported for one functionSmaller alternative, tree-shaking
Context value changing every renderMemoise the value, split contexts

16Quick Recap

  • Re-render = calling the component; it is cheap, so measure with the Profiler before optimising
  • The React Compiler memoises automatically; manual memo/useMemo/useCallback are fine-tuning
  • Move state down, lift content up, and use stable props before reaching for memoisation
  • useTransition / useDeferredValue keep typing responsive during heavy updates
  • lazy + Suspense split code by route; virtualise long lists
  • <Activity> (19.2) preserves state for hidden UI
