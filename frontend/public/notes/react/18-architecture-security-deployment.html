Architecture, Security and Deployment

Take React to production. Folder structure, code quality, accessibility, security (XSS, tokens, CSRF), error monitoring, environment configuration, build optimisation and deployment.

01Project Architecture

Feature-based folder structure

Group code by feature, not by file type. Everything for "courses" lives together.

src/
├── app/                      ← app shell: providers, router, global styles
│   ├── App.tsx
│   ├── router.tsx
│   └── providers.tsx
├── features/
│   ├── auth/
│   │   ├── components/       LoginForm.tsx
│   │   ├── hooks/            useAuth.ts
│   │   ├── api.ts
│   │   └── index.ts          ← public API of the feature
│   ├── courses/
│   │   ├── components/  hooks/  api.ts  types.ts
│   └── lessons/
├── components/               ← shared, generic UI (Button, Modal, Table)
├── hooks/                    ← shared hooks (useDebounce)
├── lib/                      ← api client, query client, utils, constants
├── pages/ (or routes/)       ← route-level components that compose features
└── test/

Guidelines

  • Co-locate tests, styles and types with the component
  • Features expose a small public API through index.ts; avoid deep imports across features
  • Shared components/ must not import from features/ (dependencies point inward)
  • Use absolute imports (@/features/courses) via paths in tsconfig and Vite alias
  • Keep pages thin: fetch data, compose feature components
  • Separate UI from data logic: custom hooks or Server Components fetch, presentational components render
  • Prefer composition over configuration with many boolean props
import path from "node:path";
export default defineConfig({ resolve: { alias: { "@": path.resolve(__dirname, "src") } } });

Rules of React (what the compiler also assumes)

  1. Components and hooks are pure: same inputs, same output; no mutation of props/state/context during render
  2. React calls components and hooks; don't call components as plain functions
  3. Rules of Hooks: top level only, from components/custom hooks only

03Accessibility (a11y)

Accessibility is part of quality and often a legal requirement (WCAG 2.2 AA).

  • Use semantic HTML: <button> for actions, <a> for navigation, <nav>, <main>, <h1>…<h6> in order, <label>
  • Don't attach click handlers to <div> (no keyboard, no role)
  • Every interactive element must be keyboard operable with a visible focus style
  • Images: meaningful alt text (alt="" for decorative)
  • ARIA only when native HTML can't do it: aria-label, aria-expanded, aria-live, role="dialog"
  • Manage focus on route changes, modals (trap + restore) and error summaries
  • Don't rely on colour; contrast ratio at least 4.5:1
  • Respect prefers-reduced-motion
  • Test: eslint-plugin-jsx-a11y, axe DevTools, Lighthouse, keyboard-only walkthrough, screen reader (NVDA, VoiceOver)

04Security

Cross-Site Scripting (XSS)

React escapes values rendered in JSX, which blocks most XSS. Risks remain:

<div dangerouslySetInnerHTML={{ __html: userHtml }} />       // dangerous: sanitise first (DOMPurify)
<a href={userUrl}>Link</a>                                    // "javascript:alert(1)" URLs execute!
<iframe src={userUrl} />   eval(userInput)   new Function(userInput)
  • Sanitise any HTML with DOMPurify before dangerouslySetInnerHTML
  • Validate URLs: allow only http:, https:, mailto: (new URL(url).protocol)
  • Add a Content-Security-Policy header (no inline script, restrict sources)
  • Never build HTML/JS strings from user input

Token storage

StorageXSS riskCSRF riskVerdict
localStorage / sessionStorageHigh: any script can read itNoneAvoid for sensitive tokens
HttpOnly, Secure, SameSite cookieNot readable by JSNeeds mitigation (SameSite, CSRF token)Preferred
In-memory variable + refresh-token cookieLowLowGood for SPAs

CSRF

If you authenticate with cookies, protect state-changing requests: SameSite=Lax/Strict, CSRF tokens or custom headers, and check the Origin header on the server.

CORS

CORS is enforced by the browser and configured on the server. It does not protect your API from non-browser clients. Allow only the origins you need; never * with credentials.

Other front-end security rules

  • Never put secrets (API keys with write access, DB URLs) in client code or VITE_* variables: everything in the bundle is public
  • Authorisation belongs on the server; hiding a button or route is only UX
  • Validate input on the server even if the client validated it
  • Keep dependencies updated: npm audit, Dependabot/Renovate; commit the lockfile; review new packages
  • Use rel="noopener noreferrer" on target="_blank" links to untrusted sites
  • Don't log tokens or personal data; avoid putting sensitive data in URLs
  • Use HTTPS everywhere and set security headers (HSTS, X-Content-Type-Options, frame-ancestors)
  • Server Functions are public endpoints: authenticate, authorise and validate each call

05Authentication Flow (Typical SPA + API)

1. POST /login            → server sets HttpOnly session cookie (or returns short-lived access token)
2. App loads → GET /me    → user profile fills the auth store
3. Requests send cookies (credentials: "include") or Authorization header
4. On 401 → refresh once; if that fails → redirect to /login
5. Logout → POST /logout, clear caches and stores

Managed options: Supabase Auth, Auth0, Clerk, Firebase Auth, NextAuth/Auth.js, Keycloak. Don't implement cryptography or password storage yourself.

06Error Monitoring and Logging

import * as Sentry from "@sentry/react";
Sentry.init({ dsn: import.meta.env.VITE_SENTRY_DSN, tracesSampleRate: 0.1 });

createRoot(el, {
  onCaughtError: Sentry.reactErrorHandler(),
  onUncaughtError: Sentry.reactErrorHandler(),
  onRecoverableError: Sentry.reactErrorHandler(),
});
  • Report errors from error boundaries and the React 19 root error callbacks
  • Upload source maps so stack traces are readable (keep them private)
  • Track Web Vitals (web-vitals package) and key user flows
  • Tools: Sentry, LogRocket, Datadog RUM, PostHog

08Build Optimisation

npm run build                              # output in dist/
npx vite-bundle-visualizer                 # see what's big
  • Code splitting per route with lazy / router lazy
  • Import only what you use (import debounce from "lodash-es/debounce"; avoid whole libraries like moment.js: use date-fns/Temporal/Intl)
  • Compress images (WebP/AVIF), self-host fonts, loading="lazy"
  • Enable Brotli/gzip at the CDN or server
  • Long-term caching: Vite adds content hashes to file names; serve with Cache-Control: public, max-age=31536000, immutable for hashed assets and no-cache for index.html
  • Set performance budgets and check Lighthouse in CI

10Internationalisation (i18n)

  • Libraries: react-i18next, FormatJS (react-intl), Lingui
  • Never concatenate translated strings; use placeholders and plural rules
  • Format with Intl.DateTimeFormat, Intl.NumberFormat, Intl.PluralRules
  • Support RTL layouts with logical CSS properties (margin-inline-start)

11Monitoring Checklist Before Launch

  • Error boundaries at app/route/widget levels, with friendly fallbacks
  • Error reporting with source maps; alerts configured
  • 404 page and offline/failed-request states
  • Meta tags, favicon, Open Graph, sitemap and robots (if public)
  • Lighthouse: performance, accessibility, best practices at or above 90
  • Keyboard and screen reader pass on key flows
  • Security headers, HTTPS, no secrets in the bundle
  • Analytics and privacy consent where required
  • npm audit clean (or understood), lockfile committed
  • Rollback plan and preview deployments

12Quick Recap

  • Organise by feature, keep pages thin, share through small public APIs
  • Enforce quality with TypeScript, ESLint (hooks + a11y), Prettier and CI
  • Build accessibility in: semantic HTML, keyboard support, focus management, contrast
  • Security: escape/sanitise, prefer HttpOnly cookies over localStorage tokens, never ship secrets, authorise on the server
  • Monitor with error reporting and Web Vitals; optimise bundles with splitting and caching
  • Deploy static builds to a CDN (with SPA fallback) or containers; automate with CI/CD
