Testing React Applications

Test the way users use your app. Vitest, React Testing Library, user-event, mocking APIs with MSW, testing hooks, async UI, accessibility checks and end-to-end tests with Playwright.

01Why and What to Test

Tests protect you from regressions and let you refactor with confidence. Aim for tests that resemble how users interact with the UI, not tests that mirror implementation details.

The testing trophy

        E2E (few)           Playwright: full flows in a real browser
      Integration (most)    React Testing Library: components + hooks + API mocks together
    Unit (some)             Vitest: pure functions, reducers, utilities
  Static analysis (always)  TypeScript + ESLint
TestExample
UnitformatPrice(2499) returns "₹2,499.00"
Component / integrationFilling the login form shows an error for a bad password
E2EUser signs up, enrols in a course, sees it on the dashboard

02Tooling

ToolRole

React Testing Library (RTL)Render components and query the DOM like a user

Note

Jest also works. Many existing projects use it; Vitest is the default choice for new Vite projects.

04Unit Tests

import { describe, it, expect } from "vitest";
import { formatPrice, cartReducer } from "./cart";

describe("formatPrice", () => {
  it("formats rupees", () => {
    expect(formatPrice(2499)).toBe("₹2,499.00");
  });
  it.each([[0, "₹0.00"], [10.5, "₹10.50"]])("formats %s as %s", (input, expected) => {
    expect(formatPrice(input)).toBe(expected);
  });
});

describe("cartReducer", () => {
  it("adds an item without mutating state", () => {
    const state = { items: [] };
    const next = cartReducer(state, { type: "added", item: { id: 1 } });
    expect(next.items).toHaveLength(1);
    expect(state.items).toHaveLength(0);
  });
});

05Component Tests with RTL

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import Counter from "./Counter";

describe("Counter", () => {
  it("increments when the button is clicked", async () => {
    const user = userEvent.setup();
    render(<Counter />);

    expect(screen.getByText(/count: 0/i)).toBeInTheDocument();
    await user.click(screen.getByRole("button", { name: /increment/i }));
    expect(screen.getByText(/count: 1/i)).toBeInTheDocument();
  });
});

Query priority (use the first that works)

  1. getByRole (with name): matches how assistive tech sees the page
  2. getByLabelText: form fields
  3. getByPlaceholderText, getByText, getByDisplayValue
  4. getByAltText, getByTitle
  5. getByTestId last resort

Query variants

PrefixNot foundFound multipleAsync
getBy…throwsthrowsno
queryBy…returns nullthrowsno
findBy…rejects after timeoutthrowsyes (waits)
getAllBy / queryAllBy / findAllByreturns array
expect(screen.queryByRole("alert")).not.toBeInTheDocument();      // asserting absence: use queryBy
const row = await screen.findByText("React 19");                  // waiting for async UI: use findBy

Common matchers (jest-dom)

toBeInTheDocument, toBeVisible, toBeDisabled, toBeEnabled, toHaveTextContent, toHaveValue, toBeChecked, toHaveAttribute, toHaveFocus, toHaveAccessibleName.

06Testing Forms and Interactions

it("shows validation errors and submits valid data", async () => {
  const user = userEvent.setup();
  const onSubmit = vi.fn();
  render(<LoginForm onSubmit={onSubmit} />);

  await user.click(screen.getByRole("button", { name: /log in/i }));
  expect(await screen.findByRole("alert")).toHaveTextContent(/email is required/i);
  expect(onSubmit).not.toHaveBeenCalled();

  await user.type(screen.getByLabelText(/email/i), "asha@mail.com");
  await user.type(screen.getByLabelText(/password/i), "secret123");
  await user.click(screen.getByRole("button", { name: /log in/i }));

  expect(onSubmit).toHaveBeenCalledWith({ email: "asha@mail.com", password: "secret123" });
});

Other user helpers: user.type, user.clear, user.selectOptions, user.upload, user.hover, user.keyboard("{Enter}"), user.tab().

07Mocking

const fn = vi.fn();                              // spy/mocks
fn.mockReturnValue(5);   fn.mockResolvedValue({ ok: true });
expect(fn).toHaveBeenCalledTimes(1);
expect(fn).toHaveBeenCalledWith("a");

vi.mock("./api");                                // mock a module
vi.spyOn(window, "fetch").mockResolvedValue(new Response("{}"));

vi.useFakeTimers();                              // timers, debounce
vi.advanceTimersByTime(300);
vi.useRealTimers();

Mock the network with MSW

npm install -D msw
import { setupServer } from "msw/node";
import { http, HttpResponse } from "msw";

export const handlers = [
  http.get("/api/courses", () => HttpResponse.json([{ id: 1, title: "React 19" }])),
  http.post("/api/enroll", async ({ request }) => HttpResponse.json({ ok: true }, { status: 201 })),
];
export const server = setupServer(...handlers);
import { server } from "./server";
beforeAll(() => server.listen({ onUnhandledRequest: "error" }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
it("shows an error state when the API fails", async () => {
  server.use(http.get("/api/courses", () => new HttpResponse(null, { status: 500 })));
  renderWithProviders(<Courses />);
  expect(await screen.findByRole("alert")).toHaveTextContent(/could not load/i);
});

MSW lets your code use the real fetch, so tests stay close to production behaviour and the same handlers work in the browser for development.

08Testing Components with Providers

import { render } from "@testing-library/react";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { MemoryRouter } from "react-router";

export function renderWithProviders(ui, { route = "/" } = {}) {
  const client = new QueryClient({ defaultOptions: { queries: { retry: false } } });   // no retries in tests
  return render(
    <QueryClientProvider client={client}>
      <MemoryRouter initialEntries={[route]}>{ui}</MemoryRouter>
    </QueryClientProvider>
  );
}

Use a fresh QueryClient per test to avoid cache leaking between tests; use MemoryRouter or createMemoryRouter for routing.

09Testing Async UI and act()

  • Prefer await screen.findBy… / waitFor over arbitrary delays
  • await user.click(…) already wraps updates in act
  • In React 19, import act from react (not react-dom/test-utils)
  • "not wrapped in act(...)" warnings mean a state update happened after the test ended or was not awaited
import { waitFor } from "@testing-library/react";
await waitFor(() => expect(onSave).toHaveBeenCalled());

10Testing Hooks

import { renderHook, act } from "@testing-library/react";

it("toggles", () => {
  const { result } = renderHook(() => useToggle(false));
  expect(result.current[0]).toBe(false);
  act(() => result.current[1]());
  expect(result.current[0]).toBe(true);
});

For hooks that need context, pass a wrapper: renderHook(() => useAuth(), { wrapper: AuthProvider }).

11Snapshot and Visual Testing

  • Avoid large DOM snapshots: they are brittle and rarely catch real bugs
  • Use inline snapshots for small, stable structures
  • For visual regression use Playwright screenshots, Chromatic or Storybook

12Accessibility Testing

import { axe, toHaveNoViolations } from "jest-axe";
expect.extend(toHaveNoViolations);

it("has no obvious a11y violations", async () => {
  const { container } = render(<LoginForm />);
  expect(await axe(container)).toHaveNoViolations();
});

Automated checks catch roughly a third of issues; also test with the keyboard and a screen reader, and use getByRole so your tests double as accessibility checks.

13Testing Server Components and Actions

  • Server Actions and pure server logic: unit-test as normal async functions (mock the database)
  • Async Server Components: RTL cannot render them directly; test the data functions with unit tests and the flow with E2E tests
  • Client Components inside them are tested with RTL as usual

14End-to-End Tests with Playwright

npm init playwright@latest
import { test, expect } from "@playwright/test";

test("student can enrol in a course", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("Email").fill("student@hanbee.test");
  await page.getByLabel("Password").fill("secret123");
  await page.getByRole("button", { name: "Log in" }).click();

  await page.getByRole("link", { name: "Courses" }).click();
  await page.getByRole("button", { name: "Enroll in React 19" }).click();

  await expect(page.getByRole("status")).toHaveText("Enrolled!");
  await page.reload();
  await expect(page.getByText("React 19")).toBeVisible();
});
  • Auto-waiting locators (getByRole, getByLabel) make tests stable
  • Run across Chromium, Firefox and WebKit, record traces and videos for failures
  • Keep E2E tests for critical journeys (sign-up, checkout, enrolment); they are slower

15Test Quality Rules

DoDon't
Test behaviour the user seesTest internal state or private functions
Query by role, label, textQuery by class names or test ids first
Mock the network boundary (MSW)Mock your own components/hooks everywhere
Keep tests independent and deterministicShare state between tests; rely on order
Write one clear reason to fail per testGiant tests asserting everything
Name tests as sentences (it("shows an error when…"))it("test 1")

16Coverage and CI

npx vitest run --coverage
  • Coverage shows untested code, not good tests; don't chase 100%
  • Run lint, type-check and tests in CI (GitHub Actions) on every pull request
  • Block merges on failures; run E2E on a preview deployment
name: CI
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit
      - run: npm run test:run

17Quick Recap

  • Test behaviour, not implementation: Vitest + React Testing Library + user-event
  • Prefer getByRole/getByLabelText; use findBy… for async, queryBy… for absence
  • Mock the network with MSW; wrap with providers using a renderWithProviders helper
  • Use renderHook for hooks; act now comes from react
  • Keep E2E (Playwright) for critical user journeys; run everything in CI
